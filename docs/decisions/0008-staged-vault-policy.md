# ADR 0008: Staged Vault Policy

- **Status:** Accepted development design
- **Date:** 2026-09-06

## Scope and review

The service-scope defaults, batch proposal format and current storage migration are superseded by ADR 0013. The original single-site design below is retained as historical context; authentication, waiting and atomic confirmation remain in force.

The user explicitly requests five-second testing defaults for Greylist waits, access duration and Vault waits, with protected controls to increase them later. These are real policy values, not an authentication bypass or debug override. This build permits 5 seconds through 24 hours for Greylist wait/access duration, and 5 seconds through 30 days for Vault wait. Longer production defaults and minimums require a separate release decision.

One pending proposal may combine one hostname change, timing changes and a password replacement. The hostname change may add, expand or remove one independent Whitelist scope; additions and removals cannot be combined. The current password authenticates staging and confirmation. Confirmation names the exact proposal ID and base policy revision, and cannot occur before its captured eligibility deadline. Editing replaces the proposal and starts the full current Vault wait again. Cancellation discards the proposal without changing policy. No change, including an increased restriction, takes immediate effect. Reducing the Vault wait itself must wait through the old value. The interface recommends including subdomains but review preserves the explicit chosen scope. Removing a parent scope also removes redundant covered Whitelist children, while Blacklist entries cannot be removed or overridden.

The Core Vault service owns validation, timing, revision checks and state transitions. A shared store transaction lock serializes Vault and Greylist operations, including authentication and their read/commit boundaries. Policy, pending proposals, credential verifiers and cooldowns share a versioned DPAPI envelope. A password proposal contains only a separately salted PBKDF2 verifier generated by the existing Windows authentication adapter; never plaintext. Confirmation atomically replaces the verifier, policy revision and pending state. The old password remains valid until this write succeeds. Forgotten-password recovery is not provided by this flow.

Version 1 data migrates to the current version, retaining the existing password and pending Greylist deadlines while creating the development Vault policy. Version 2 data migrates once to version 3 with a null removal field, preserving its Vault state and any pending proposal. Version 3 makes that field mandatory so deleting it fails closed rather than silently changing a reviewed proposal. Current policy settings and entries must be present and valid; corruption must not reset to starter policy. Before initial credential setup only the existing starter policy is available. Once initialized, unavailable durable policy denies navigation. New installations and the version-1 development migration receive the user-authorized five-second defaults; later launches never reset configured timings.

Greylist requests capture their wait and grant duration at the first challenge. Later policy changes do not shorten existing deadlines or lengthen their grants. Confirmed policy revisions clear session grants on the next authorization check. New requests use current settings. Sphere search and bookmarks read current policy, not the historical starter directory.

Retain the existing atomic-write, single-instance lease, retry-delay and clock-anomaly defenses. The same local-user/offline-clock limits described in ADR 0007 still apply; this is not hardened anti-tamper storage. A corrupt current envelope is not silently rolled back to an older policy or password.

Atomic replacement retains the previous protected envelope for future controlled recovery. Current-schema mandatory fields must be present; deserialization defaults must not silently weaken an initialized policy. The native editor supports seconds, minutes, hours and days, but conversion is presentation-only and Core validates the resulting durations.

## Verification

Proposal normalization is shared between read-only review, staging, confirmation and persisted-state validation. The editor invalidates its review when any proposed value changes, and staging checks the reviewed policy revision before authenticating. Closing settings clears password fields and detaches completion callbacks; an already authorized save may finish, but must not update the closed window.

Use fake clocks to test early confirmation, restart, replacement/cancellation, stale IDs, old-delay protection, credential rotation, invalid host/scope, Blacklist precedence, failed writes and clock anomalies. Test version-1 migration and corrupt initialized state using isolated DPAPI files. Exercise the actual native editor, dynamic Sphere directory and access settings with a temporary WebView2 profile.
